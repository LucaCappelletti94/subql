# CHANGELOG

All notable changes to subql are recorded here. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/) and the project adheres to pre-1.0 semantic versioning (breaking changes are allowed in minor releases until 1.0).

## Unreleased

### Changed

- A table's predicates are a persistent map rather than a slab, its hash index likewise, and dropping a predicate patches the candidate indexes rather than rebuilding them from every survivor. Registering one subscription used to copy every predicate on the table, and unbinding the last binding of a predicate used to rebuild `HybridIndexes` from scratch, so both grew with the table. With a distinct filter per subscription, registration falls from 246us to 36us and unbinding from 647us to 21us at 4000 subscriptions, and both are near flat in the table's size. A removed predicate's id is released and handed out again before a fresh one, so the id space stays as dense as the slab's was and a churning partition does not walk its candidate bitmaps towards the `u32` ceiling. A shard's predicates are sorted before they are written, since a map has no iteration order to inherit.
- A term reads the caller field its own spelling names, and `describe_terms` says which. `rls2fga` now reports on every compiled term whether its caller side is the identity or a declared set, and subql carries that as `term::TermCaller` on `TermPlan`, `MembershipTermDescription` and `CallerTermDescription`. A term whose caller is `Identity` seeds from `SubscriptionRequest::subscriber` alone, and one whose caller is `Subjects` seeds from `SubscriptionRequest::subjects`, whether it is a membership subquery or a caller comparison. This supersedes the entry below stating that a membership subquery matches by `subjects` whatever it reads: a membership written `user_id = current_setting('app.user_id', true)` reads one session value in the database, and matching it against a set admitted rows a key grants that the registered query never returns. Such a term now requires `subscriber`, ignores `subjects`, and refuses a stated value row granted by anything but that one value.
- Registering and unbinding a subscription no longer copy the table's whole binding state. A predicate's reference count lives in the store rather than inside the predicate, so taking or dropping a reference stops deep-copying every predicate on the table to change one integer, the binding, session, consumer-bitmap and binding-lookup indexes are persistent maps whose mutation rewrites one path, and unbinding answers "does another binding hold this predicate and consumer" from `binding_lookup` and "is this consumer still referenced" from a maintained count, where both used to walk every binding. On a table whose subscriptions share one filter, registration is flat at 17us instead of growing from 29us to 80us by 4000 subscriptions, and unbinding costs 5us instead of 138us. With a distinct filter per subscription both remain proportional to the table, 247us and 660us against 412us and 1.05ms, because adding or removing a predicate still copies the predicate slab.
- The membership term index is a persistent map, so a membership event no longer copies the admissions of the term it touches. `TermMembers` holds its value, subscriber and grant tables as `rpds::HashTrieMapSync`, whose clone shares the trie's nodes and whose insert rewrites one path, which is what the partition's copy-on-write clone needs from it. On the `term_events` benchmark a membership event against 2000 subscriptions sharing one term predicate falls from 1.18ms to 1.9us, and against 2000 three-subject callers from 2.71ms to 3.7us, with the cost now flat in the table's size rather than proportional to it. Row dispatch reads the same index and is unchanged, 976ns against 994ns at the same size.
- A membership event no longer copies the whole partition. Every index of `PredicateStore` is held behind its own `Arc`, and `term_members` holds one `Arc<TermMembers>` per `(predicate, slot)`, so the copy-on-write clone each mutating dispatch takes copies seven pointers and deepens only into the index it changes. A membership row arriving at a table carrying one term subscription and 2000 ordinary row subscriptions beside it cost 373us and grew with the row subscriptions it never reads; it now costs 3.7us and is flat in them. A table whose subscriptions all share one term predicate is unchanged, since that is one slot and the slot is what the event rewrites. Measured by the new `term_events` benchmark.
- A caller is a set of subjects rather than one value. `SubscriptionRequest::subscriber` now states only the single value a caller comparison admits, since that SQL reads one session value and admitting a union there would deliver rows the registered query does not return. The new `SubscriptionRequest::subjects(impl IntoIterator<Item = Value<B>>)` states the subjects a membership subquery matches the caller by, and a changed membership row naming any of them moves what the filter admits, which is what the same subquery does in a database reading the whole set out of its own session setting. A filter naming a membership subquery is refused with no subjects, exactly as it was refused with no subscriber, and a subject whose kind is not the membership subject column's is now refused at registration instead of silently matching no row.
- Membership admissions are attributed to the subject that granted them. `MembershipTermDescription::seed_sql` projects the membership subject column ahead of the compared values, and `SubscriptionRequest::term_values` takes each row as that subject and the values it grants, so a value two of a caller's subjects grant survives either one of them losing its membership. Unattributed, the first withdrawal would take that value away for good, since nothing re-adds a membership that never changed. A membership change that moves nobody now reports no `TermNarrowing` at all, where previously every ordinal claiming the subject was reported as having moved.
- Grouped aggregate identity now uses a backend-selected, versioned canonical key whose equality matches each supported database `GROUP BY` rule. PostgreSQL folds floating-point signed zero and NaN payloads, deterministic text collations, and structural `jsonb`. MySQL folds normalized decimals and supported binary collations. SQLite folds signed zero, built-in text collations, and lossless JSON storage classes. Unsupported kinds refuse the folded tier, and an unexpected runtime value demotes under the same subscription identity with `MaintenanceStopReason::GroupKeyUnencodable`.
- Connector reads now take `ReadQuery`, which carries SQL and typed bind values. Grouped `MIN` and `MAX` refreshes bind group values natively instead of rendering SQL literals. Sync, async, paged, scalar, aggregate-seed, and PostgreSQL cursor reads share the same contract.
- `SubscriptionEngine::register_batch(specs)` now guarantees per-index parity with calling `register(spec)` in a loop. Two divergences are closed. First, within-batch idempotent duplicates now collapse onto the first occurrence's `SubscriptionId` (matching the sequential dedup path) instead of being assigned fresh ids. Second, when an active eviction policy is configured (anything other than `Reject`), the implementation transparently falls back to a sequential `register()` loop so within-batch evictions can see pending sub_ids the bulk path could not. Surfaced by `tests/proptest_register_batch_parity.rs`.
- `AsyncAutoResolvingEngine::with_max_concurrent_reexecutions(usize)` now configures a **persistent** global concurrency cap on re-execution connector calls. Previously the cap applied per `consumers_batch` call only (consumed by `buffer_unordered`) and was ignored by per-event `consumers`. The cap is now honored by both flows and persists across calls via an `async_lock::Semaphore` stored on the engine. `cap = 0` is normalised to 1 to avoid a deadlock.
- `TablePartition::select_candidates` now selects for one row image and takes neither an `EventKind` nor a changed-column list. An UPDATE goes through the new `select_update_candidates()`, on both `TablePartition` and `HybridIndexes`, which returns every predicate delivering whole rows from the new `HybridIndexes::full_row` bitmap. `HybridIndexes::add_predicate` takes the predicate's `QueryProjection` in place of its `is_agg` flag, and `HybridIndexes::dependency_free` is removed, since nothing read it once row UPDATE candidates stopped coming from the dependency index. Row dispatch now evaluates every row predicate registered on the table for each UPDATE, which is what whole-row delivery costs, and in exchange `consumers()` no longer computes `changed_columns` on the row path at all. The changed-column prune can only come back for a row projection narrower than every column, which subql does not offer. The dependency index keeps its two readers, undecodable cells on INSERT and DELETE, and the aggregate prune.
- `Shapes::diff` now hands back the facts and the queries the change obliged as two values, `(StoreDiff, Requeries)`, where it previously returned one `StoreDiff` carrying `requeries` as a third public field. `StoreDiff` consequently holds only `added` and `removed` and needs neither a lifetime nor a backend parameter, and `OpenFgaPolicy::apply` takes `&StoreDiff`. The queries are what no single row settles, so nobody but the caller can run them, and a caller who ignored the field left every such fact exactly as it was before the change. In the allow direction that is a row handed to somebody whose access has already gone, and no later correction takes it back. A caller can no longer receive the facts without also receiving the queries and saying what becomes of them.
- `AutoResolvingEngine::apply` and both dispatch traits' `consumers` now hand back a `#[must_use]` `Dispatch` that borrows the engine, and its notifications are reachable only by draining it through `Dispatch::resolve` or `Dispatch::resolve_collect`. Previously the notifications came back while the reads that same event required waited in the engine's queue behind a separate `resolve_collect`, so a caller who took them and never drained lost every triggered read with no error, no warning and no log line. `SubscriptionDispatch::Notifications` and `AsyncSubscriptionDispatch::Notifications` are consequently generic over that borrow, which is a source break for any downstream implementor. The drain hands back `Settled`, carrying the in-process half and the read half separately, so a read that fails keeps its failure in `Settled::reads` while the notifications the fold already produced still arrive. A caller that drains on a schedule of its own, batching several events so their reads coalesce into one, opts in by name through `AutoResolvingEngine::apply_leaving_reads_queued`.
- An asynchronous drain abandoned before it finishes, by a timeout, a losing `select!` arm or an aborted task, no longer destroys the in-process notifications it was carrying. They are parked on the engine synchronously with the call rather than inside the future, since an `async fn` body waits for its first poll while the guard is consumed at the call, and they are claimed with `AutoResolvingEngine::take_undelivered`. Applying another event while they are held returns the new `DispatchError::UndeliveredNotifications` rather than folding over what nothing else can produce again, because the abandoned event committed exactly once before any read ran.
- `MaterialiseError` is renamed `ReconcileError`, since `OpenFgaPolicy::reconcile_store` fails with the same four causes. Its `Contradiction` variant also covers two rows of one load stating one fact under different conditions.
- Dispatch decodes each cell of an event at most once per row image, however many predicates read it. `ResolvedEvent` caches the decoded cells of wire formats that decode on every read (wal2json, pgoutput, Maxwell), and the VM refers to a text, byte, decimal, document or custom literal or cell instead of copying it. Measured in instructions per event under cachegrind: wal2json dispatch over 100 predicates falls by 48 percent and over 1000 `LIKE` predicates by 66 percent. Events that already hold decoded values run 2 to 4 percent more instructions on integer-heavy predicates.
- `Backend::LIKE_ESCAPE` and `LikeEscape` are replaced by `Backend::LIKE_DEFAULT_ESCAPE` and `Backend::LIKE_DANGLING_ESCAPE`. The two were paired on the ground that an engine with no default escape has no dangling one, and an `ESCAPE` clause gives SQLite one, which measured, answers no-match.
- Shards are written as version 15, and a version 14 shard is refused on load. A stored program for `n = 3 AND flag` failed every dispatch and would have kept failing after the fix below, absorbing any fresh registration of the same filter, and a stored `LIKE` now carries its escape character, so its encoding changed. A store holding a version 14 shard fails to load with `StorageError::VersionMismatch`, so its subscriptions are registered again into a fresh store.
- A `COUNT` refused at registration is refused in the words every aggregate uses, for example `COUNT(...) FILTER (WHERE ...) not supported`, and still says that `*` is accepted.
- A text comparison refused because its column compares under the database default collation, which the catalog cannot name, says so, where the refusal said the column declares a collation.

### Added

- A projection naming a subset of the table's columns, as in `SELECT id, status FROM orders WHERE status = 'paid'`, is served in process as the new `QueryProjection::Columns { columns, carries_key }`, which `Served::projection` exposes with the columns in the order written and whether they carry the primary key, so the consumer trims its own events. It filters as `SELECT *` does, and an UPDATE that changes none of the projected columns is not reported, since nothing the result holds changed. Such a statement was a keyed read per change, delivering the unchanged row on that UPDATE, and one without the key was a whole re-read. A subset need not carry the key. One that does is applied by key, so an UPDATE or DELETE whose old image lacks a projected cell, as PostgreSQL's default replica identity sends it, is reported as usual. One that does not may be held as a bag whose rows are removed by their projected values, so there such an UPDATE or DELETE is reported unanswered, and on a default-identity PostgreSQL table every one of them is. `QueryProjection::delivers_rows` answers whether a projection delivers row events. A column is accepted bare, renamed, or qualified by the table read, and anything else is routed to a read.
- `COALESCE` is served in process wherever a value is read, as a comparison or arithmetic operand, the tested side of `IN`, `BETWEEN` and `LIKE`, and as a condition, through the new `Instruction::Coalesce`. It is served when its column arguments share one declared type and collation in the integer, float, decimal, text or boolean family and its literals are written in that family's own form, and it then compares and computes as that column does, collation and width included. A cell the event did not carry ahead of the first present argument leaves it unanswered and names the column. Every other mix, a call of one argument, an argument that is neither a column nor a literal, and a literal compared with it in another family's form are routed to a database read, since the engines type those apart: measured, `COALESCE(1, 2.5) / 2` is `0.5` on PostgreSQL and MySQL and `0` on SQLite, and `COALESCE(NULL, 1) = '1'` is false on SQLite only.
- `LIKE` and `ILIKE` with an `ESCAPE` clause are served in process, where they were routed to a read. The written character replaces the engine's default escape, so a backslash is ordinary under `ESCAPE '!'`, and `Instruction::Like` carries the escape resolved at registration. The new required `Backend::like_escape_clause` says what a written clause means on each engine, measured: one character escapes everywhere, `ESCAPE ''` is no escape on PostgreSQL and is routed on SQLite, which rejects it, and on MySQL, where it turns on the session's `NO_BACKSLASH_ESCAPES`, and MySQL also routes a character outside ASCII, which it rejects. A pattern ending with the written escape answers by the engine's own rule, raising on PostgreSQL and not matching on MySQL and SQLite.
- Null-safe equality is served in process, `IS [NOT] DISTINCT FROM` on PostgreSQL and SQLite and `<=>` on MySQL, through the new `Instruction::NotDistinct`, and compares two `NULL`s as equal and a `NULL` against a value as distinct. A cell the event did not carry leaves it unanswered and names the column. Its operands are classified exactly as `=` classifies them, so a collation or a pair of kinds `=` leaves to the database is left to it here too. Each engine serves only the spelling it accepts, named by the new required `Backend::NULL_SAFE_EQUALITY`, and the other spelling is routed to a database read: MySQL rejects `IS DISTINCT FROM` and PostgreSQL and SQLite reject `<=>`. Two spellings of one null-safe equality or truth test share one predicate, as two spellings of `=` do.
- `IS [NOT] TRUE`, `IS [NOT] FALSE` and `IS [NOT] UNKNOWN` are served in process over a condition or a boolean column, through the new `Instruction::IsTruth`, so an unknown condition answers decisively as the engines answer it. An unknown that read a cell the event did not carry stays unanswered. SQLite has no `IS [NOT] UNKNOWN`, which the new required `Backend::READS_IS_UNKNOWN` states, so there it is routed to a read. A non-boolean operand is routed too, since PostgreSQL raises on it where MySQL and SQLite read a number's truth.
- A membership subquery or a caller comparison under a truth test or a null-safe equality is routed to a database read. Either construct can negate what it wraps, and `(owner = current_setting('app.user_id', true)) IS NOT TRUE` would otherwise admit every subscriber but the caller.
- A filter the database answers row by row is served by the keyed tier when its projection renames the primary key, as in `SELECT id AS order_id, status FROM orders WHERE lower(status) = 'paid'`. The key is read from the column written before the alias, so swapped names do not move it, and a computed value carrying the key's name is not taken for the key. Such a projection was served only by re-reading the whole statement on every change to the table.
- `SELECT q.* FROM t` is served in process as `SELECT *` when `q` names the table read, its alias when one is written and its name otherwise. It was refused as a qualified wildcard, so it reached only a tier re-reading the statement on every change to the table. A qualifier naming another table is still refused.
- `RegisterError::UnboundPlaceholder { placeholder }` names a `$N` or `?` placeholder no bind value resolves, whether the request carries no binds or too few. Registering `WHERE qty = $1` without binds was refused with an internal literal type error, and too few binds with `BindResolution`.
- `OpenFgaPolicy::reconcile_store(records, replayer)` makes the store equal to the database over every region the translation owns, and reports what moved as one `Reconciled` per region that changed. `write_records` only adds, `reconcile_records` deletes inside one keyed slice and `materialise` inside one group's region, so a fact the store held and the database no longer did, which is what restoring the database from a backup leaves, survived every boot. `records` is the whole load, every row every tuple query returned. Each region of the new `Shapes::load_regions`, the regions a row-settled or keyed shape maintains alone, becomes what those records state, and every group's region becomes the union of its replays. The store is read once, every difference is computed and every contradiction refused before the first write, facts outside every declared region are left alone, and a store already equal to the load sends nothing. `Reconciled::is_empty` says whether a reconcile moved anything.
- `<column> = ANY(<columnless call>)` compiles wherever `<column> = <columnless call>` compiles, as the set-valued caller side: in a membership subquery's `WHERE`, in the bounded `EXISTS`, and as a caller comparison on the outer statement, so `owner = ANY(string_to_array(current_setting('app.subjects', true), ','))` and `project_id IN (SELECT project_id FROM project_members WHERE user_id = ANY(...))` register once the translator declares `app.subjects` as a `SetAttribute`. A columnless call may now nest columnless calls, which is what the `string_to_array` spelling needs. The seed read keeps the set predicate verbatim, so it returns every row any of the caller's subjects grants and projects which one, and the engine admits a row to the caller while any held subject grants it.
- A filter comparing a column to the caller directly (`WHERE owner = current_setting('app.user_id', true)`, either operand order) now compiles as a membership term instead of being refused as unsupported SQL. The term seeds itself from `SubscriptionRequest::subscriber`, so one compiled predicate serves every subscriber and no seed read exists for it (`describe_terms` reports nothing for the comparison). Registration asks `rls2fga` whether the call names the caller, so an undeclared setting key such as `app.tenant_id` is refused in the classifier's wording, a subscriber of another kind than the compared column is refused naming both kinds, stated `term_values` for the compared column are refused, a registration without a subscriber is refused naming the missing subscriber, and `NOT` over the comparison stays unsupported SQL because its negation admits rows through a NULL cell that SQL admits for nobody. `TermPlan` now carries its movement as `Option<TermMovement>`, `None` for a caller comparison, and `TermKey::scalar_kind()` reports the kind a key holds.
- `SubscriptionDispatch::consumers` answers the whole event on every engine that implements it. `AutoResolvingEngine` already meant the whole event by it, while `SubscriptionEngine` meant the half it serves from the event itself, so code written against the trait folded aggregates and triggered reads with one engine and silently did neither with the other. The engine's implementation routes through `dispatch` and its `Notifications` type is now `DispatchOutput`. The inherent `SubscriptionEngine::consumers` still answers the in-process half, which is a choice a caller makes knowingly, and says so.
- `SubscriptionEngine::unregister_subscription` ends an answer from whichever registry holds it, so `false` means no answer had that id rather than the answer being of the other kind. One counter hands out ids for maintained answers and read answers alike, and a caller holding one cannot tell which registry took it, so ending a read answer by id used to report failure while leaving it registered, persisted and notified. `AutoResolvingEngine::unregister_subscription` no longer resolves the two registries itself, since the engine does.
- `AutoResolvingEngine::unregister_query` drops the resolve contexts and queued reads of the answers it ends, which its sibling removal paths already did. Left behind, a queued read outlived its subscription and the refusal for a read with no context did not catch it, because the context was still there: the next resolve ran a database read for an answer the engine no longer held, failed, and left the read queued for the next resolve to repeat, with no way to drain it short of dropping the engine. One statement can name several answers, so the contexts whose subscription neither registry holds any more are the ones dropped.
- Ending an answer rewrites what a restart reads, so it no longer revives. Neither file was written on removal, only on capture, so `unregister_reread`, `unregister_subscription`, `unregister_session` and `unregister_query` left a caller's deletions behind and a restart brought them back. A maintained answer came back from its table's shard and went on notifying the consumer that ended it, so a removal rewrites that table's shard as well as the reads file. A session writes each of its tables once rather than once per answer it held, and a failed write after a removal is logged rather than raised, since ending cannot be undone and the caller has already been told it happened.
- `SubscriptionEngine::snapshot_table` rewrites the reads file as well as the table's shard. The reads file was written only when a re-read answer was captured, so a workload whose subscriptions are all answered in process wrote no statements at all and those answers came back from a restart unable to read. A shard holds each predicate as a `WHERE` expression and the statement lives only in the reads file, so the two are written together. The reads file covers every subscription rather than one table's, so a snapshot now costs one whole rewrite of it, and it is written before the shard so a failure leaves nothing committed. Restoring keeps only the statements of subscriptions the shards brought back, so a statement whose predicate was never saved, or whose answer was ended before the restart, is not reported as recovered.
- `MergeJobId` is a `#[must_use]` newtype rather than an alias for `u64`, and `SubscriptionEngine::pending_merges` names every merge still outstanding while `complete_ready_merges` swaps in the ones that have finished. The id a background merge returns was the only way to reach it, so dropping one left the merge finished, its payload held in memory and its shard never swapped into the live partition, with nothing able to name it again. Call `MergeJobId::new` and `get` where the raw number is needed. `complete_ready_merges` stops at the first failure and returns `MergeDrainError`, which carries the reports of the merges it swapped in before it, since swapping cannot be undone and those jobs are gone from the manager.
- `SubscriptionEngine::with_storage` returns a `Restored` guard rather than a tuple, and `AutoResolvingEngine::adopt` is how a reopened engine's answers get the context their reads run under. Registration is what supplies that context, and a restored answer never passes through registration, so wrapping a reopened engine in `AutoResolvingEngine::new` used to abort the process on the first event that touched a restored answer. A read for an answer that was never adopted is now refused as `ReExecError::Unadopted` instead of panicking, and `Restored::into_parts` is the named way past adoption for a caller that maintains its answers itself.
- The reads file records the statement of every subscription, including the ones the engine maintains itself, and its version moves from 4 to 5. A shard holds a compiled predicate, which is a `WHERE` expression rather than a statement, so an in-process filter restored from shards had nothing to read with when the stream could not answer it. `RestoredReads::in_process` reports those answers and `adopt` gives them a context too. As with every earlier version move, a file written by an older build is refused rather than read.
- `PgStreamingCdcSource::unacknowledged_bytes()` reports the distance between the furthest position this source has seen on a frame and the position it last reported back as flushed, and `acknowledged_position()` reports the latter as an `Option<PgLsn>`, `None` until the first acknowledgement. Acknowledging is what releases a slot, so a consumer that never acknowledges retains WAL until the server's volume fills, and the only symptom subql could previously offer was a transport error at a layer with no visible connection to the cause. A sustained rise in the figure is now alertable before the disk answers for it. A keepalive carries the server's own WAL end and a data frame carries the position of the record it holds, so the figure counts WAL this publication never carries and rises on activity elsewhere in the cluster. It is close to what the slot retains without being it, since the server retains to the slot's `restart_lsn`, which lags the confirmed flush position, so `pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn)` from `pg_replication_slots` remains the size itself.
- Per-`(session, subscription)` resume cursor on `SubscriptionEngine`. Materializer-pushed model: explicit `advance_cursor(session_id, sub_id, checkpoint)` after each successful dispatch. Monotonic by default (a rewind returns `AdvanceCursorError::NonMonotonic` without mutating). `force_set_cursor(...)` is the snapshot-bootstrap / recovery escape hatch. Reads via `cursor_for(...)` and `cursors_for_session(...)`. Explicit removal via `drop_cursor(...)`. Cleanup is automatic on `unregister_session(...)` (drops every cursor for that session) and `unregister_subscription(...)` (drops every cursor for that subscription across every session). Cursors are stored as `OpaqueCheckpoint` so the engine stays free of a struct-level `C: Checkpoint` generic. The materializer serialises its concrete checkpoint type at the boundary. In-memory only. On engine restart every client gets a full re-sync on reconnect.
- `AdvanceCursorError::NonMonotonic { previous, attempted }` returned by `advance_cursor` on a rewind attempt.
- `AsyncAutoResolvingEngine::inflight() -> usize` reports the number of re-execution permits currently held (concurrent connector calls in flight). Returns 0 when no cap is configured.
- `AsyncAutoResolvingEngine::concurrency_cap() -> Option<usize>` reports the configured cap.
- `async-lock` dependency (runtime-agnostic `Semaphore`, `no_std + alloc`).
- `tracing::trace!` event on every permit acquire when the `observability` feature is enabled.
- `patchset::apply_diffset_bytes_with_catalog(...)` and `patchset::apply_diffset_bytes_async_with_catalog(...)` apply a client-uploaded SQLite session diffset given only a catalog (`&DB: DatabaseLike`), with no `SubscriptionEngine` in scope. The async entry returns an `impl Future + Send` that owns its reconstructed batch and never borrows the catalog, so a shared `&catalog` (for a `Sync` catalog such as `ParserDB`) serves concurrent applies on a multi-thread runtime with no per-write allocation. `SubscriptionEngine::apply_diffset_bytes` and `apply_diffset_bytes_async` now delegate to these, behavior unchanged.
- `visibility` module: the authorization seam for "which of these watchers may see this row". `VisibilityPolicy` asks once per changed row naming every watcher and writes one `Verdict` per watcher, positionally, into a caller-owned buffer, so a duplicate watcher stays two answers and no allocation happens per event. `Verdict::reset` sizes that buffer and pre-fills it with `Verdict::Deny`, which is what makes a partial failure fail closed for everything it did not reach while keeping the verdicts it did write. `VisibilityPolicy::may_write` is the write peer: one watcher, one `WriteOp`, one verdict, where an error means "could not determine" rather than "denied". The row arrives as a `RowView`, a lazy per-column accessor bound to one version of the row, so an implementation that reads two columns of twenty pays for two. `EventRow::current` and `EventRow::previous` build those views over any `CdcEvent`, which is how a caller names which version a question is about. Both return `Option`, refusing a version the event does not carry (a pre-image of an insert, a post-image of a delete, either of a truncate) and a table the catalog does not know, rather than producing a view that reads every column as `Value::Missing`. That refusal is structural: a Postgres update whose old image is absent under `REPLICA IDENTITY DEFAULT` is indistinguishable from a populated one without decoding, so a caller asking about previous versions still has to require `FULL`. subql defines the trait and ships nothing behind it: the backend is the implementor's choice, following `Connector`.

### Fixed

- `x NOT BETWEEN low AND high` with a `NULL` bound selects a row the other bound already excludes, as every engine does. `b NOT BETWEEN 1 AND NULL` with `b = 0` was withheld, because a `NULL` bound made the whole test unknown where only its own side is.
- A `LIKE` whose operand is not a text column, a string, a bound parameter or `NULL`, as in `a LIKE '1%'` over a number, is routed to a database read. MySQL and SQLite match a number or a boolean by its text rendering and PostgreSQL refuses it, and subql answered no-match.
- Arithmetic over text or a boolean, over two numeric kinds, and `%` over anything but integers is routed to a database read. `a * r > 0` over an integer and a float column, `(- s) IS NULL` over text and `(r % 2) = 0` over a float were served in process as `NULL`, where every engine computes a number or refuses.
- `IN` over a text column reads the column's collation as `=` does. It compared bytes, so `folded IN ('a')` over a case-insensitive collation was served in process and missed a stored `'A'` the database selects, where `folded = 'a'` is left to the database. It is now left there too.
- Parentheses no longer hide a column's collation from a comparison. `(label) < 'b'` over a column whose ordering the build cannot reproduce was served in byte order, where `label < 'b'` is left to the database.
- A boolean column read as a condition beside `AND` or `OR`, or under `NOT`, as in `WHERE n = 3 AND flag`, no longer fails every dispatch with a VM type error. It reads as the column's own truth wherever a condition is read, which on SQLite is any nonzero stored integer, so `WHERE flag` over a stored `5` now selects the row as SQLite does, where it was compared with `true` and missed. Any other bare value read as a condition, as in `WHERE n` or `WHERE COALESCE(n, 0)`, is routed to a read, where it was compared with `true` and missed every row MySQL and SQLite select for a nonzero number.
- A condition where a value is read, as the operand of a comparison, of arithmetic, of a null-safe equality, or of `IN`, `BETWEEN` or `LIKE`, as in `(status = 'paid') = true`, is routed to a database read, where registration failed with a literal type error.
- `IN` and `BETWEEN` read their literals at the kind of the column the tested side reads, through arithmetic as `=` does, so `amount + 1 IN (5, 6)` and `amount * 2 BETWEEN 7 AND 9` are served in process, where registration failed with a literal type error. A tested side reading no column is routed to a database read.
- `SubscriptionEngine::dispatch`, and the auto engine through it, reports an aggregate whose filter the engine refuses for the event in `notifications().evaluation_failures()`, beside the refused rows, with the consumer its subscription is bound for. Such an event produces no fold, trigger or transition, so without the report it was indistinguishable from an event that moved nothing.
- The asynchronous `Dispatch::resolve` and `Dispatch::resolve_collect` futures are declared `Send`, as `AsyncSubscriptionDispatch::consumers` already was, so an `async fn` generic over the connector can hold the `Dispatch` across its drain and be spawned. The drain was `Send` in fact but only by leakage, and a leaked auto trait does not reach a caller through the trait's associated type, which rustc reports as `lifetime bound not satisfied` with no capture named. The `Send` bounds the trait impl asks for now also gate the two drains, and the engine's concurrent read phase pushes its reads into a `FuturesUnordered` rather than mapping a closure over them, since a closure taking a reference is higher-ranked and rustc cannot then prove the enclosing future `Send`.
- A caller term is reachable from the typed diesel API. Diesel renders a call's arguments as binds, `current_setting($1, $2)`, and placeholder resolution walked neither a function's arguments, an `= ANY(...)`, nor a membership subquery's `WHERE`, so the placeholders reached `rls2fga` unresolved and every caller comparison and membership subquery registered through `register_select_typed` was refused as naming no caller. It now resolves them, and a `bool` bind renders as its literal, where it was refused as unsupported.
- `visibility::transitions` now sizes and pre-fills its own scratch buffer on every call, where sizing it was previously the caller's business through a public `Transitions::reset`, which is now private. The function never writes `Transition::Withdraw` itself. Its two passes only upgrade to `Deliver`, or, when both row images deny, to `Nothing`, so `Withdraw` was the answer only because `reset` had pre-filled it. A caller reusing the buffer across events without resetting therefore kept the previous event's `Deliver` for a watcher the current event denies, which is a row delivered to somebody whose access has gone, and a caller who never reset at all read an empty buffer and delivered nothing to anybody. The reset now happens before every early return, so a refused truncate or an unknown table leaves every watcher withdrawing rather than holding the last event's answers.
- `PollingPgCdcSource` now retains an event until it is acknowledged, which is what `CdcSource::ack` has always promised and what `PgStreamingCdcSource` already did. The loop read with `pg_logical_slot_get_binary_changes`, which consumes, so `confirmed_flush_lsn` advanced before the consumer had seen anything and `ack` was a documented no-op. Every event buffered in the internal channel, up to `buffer_capacity` of them, therefore died with the source on a drop, a crash or a shutdown, and nothing could replay them because the slot was already past. The loop now peeks, which leaves the slot alone, and an acknowledgement is what releases it. Postgres reports every row of a transaction at the transaction's own position and only its commit at a later one, so an acknowledgement names a transaction rather than a record, and the loop holds the commit position of each delivered transaction and releases with a bounded `pg_logical_slot_get_binary_changes` that stops at that commit. A transaction whose commit the loop never observed stays outstanding, which costs a re-read and never a loss, and a repeated peek delivers each event once. The guarantee has a price a caller now pays. Under the consuming read a consumer that never acknowledged was fine, because `ack` did nothing, while now Postgres retains the WAL behind the slot and every poll re-reads the whole unacknowledged history, both without bound, so acknowledging is no longer optional.
- `WithdrawnFact` now carries `context: Option<RecordContextValue>`, the condition context the deleted tuple was stored under, in the same currency an added `Record` states its own in. `reconcile_records` and `materialise` held that context in the map they differenced and discarded it, so a conditional grant, whose subject is the wildcard, was reported withdrawn as a triple naming nobody, and a consumer narrowing the announcement to the bearer it withdrew had to either decode the object id or read the store again. A context holding a value no record can write, which is anything other than a string, reports `None` rather than a rendering invented for it.
- PostgreSQL `jsonb` equality now normalizes arbitrary-precision numeric spellings, so values such as `1`, `1.0`, and `1.00` compare as PostgreSQL does. Equality predicates on PostgreSQL `json` are refused because PostgreSQL defines no equality operator for that type.
- A visibility shape reading a column whose declared kind the row side cannot answer now refuses instead of silently stating no records. The loading SQL spells every kind through `::text`, while `render_text` spells only text, integer, UUID, boolean, and the timestamps, so a shape keyed on a `DATE`, `BYTEA`, `DOUBLE PRECISION`, or `NUMERIC` column, a guard reading the wrong kind (`IsTrue` over non-boolean, a comparison over an unspellable kind), a JSON path into a scalar column, or a column the catalog does not know loaded real records that no changed row could ever produce or withdraw. `is_evaluable` now takes the catalog and settles this once at setup, such shapes land in `Shapes::uncovered` under `UncoveredReason::UnreadableColumn`, and `records_from_row_view` returns the new `RowRecordError::UnreadableColumn` naming the column and its kind. An exhaustive test pins the gate to exactly the kinds `render_text` spells.
- Term slots are now numbered in normalized-text order rather than source order, and the compiled `TermTruth` operands are rewritten to match. Predicate sharing keys on the normalized WHERE text, which sorts `AND`/`OR` conjuncts, so two spellings of one multi-term filter share one predicate while each registration seeded by its own compile's slot numbering: a subscription written with reversed conjuncts stored one column's values where dispatch reads another's, so its own rows never arrived and rows whose columns held each other's values arrived wrongly. `describe_terms` consequently reports descriptions in normalized order, not source order.
- An UPDATE now notifies every row subscription whose predicate the row satisfies, whichever columns the statement changed. Candidate selection used to narrow an UPDATE to the predicates reading a changed column. That answers whether a verdict can flip, not whether the row image a subscriber holds went stale, so a `SELECT * FROM orders WHERE quantity > 0` subscription never heard about `UPDATE orders SET status = ...` and its replica kept serving the old `status` until something touched `quantity`. The same narrowing also dropped view exits whenever a source reported no changed columns at all, which `pg_walstream::ChangeEvent` does for any old image narrower than the whole row (`REPLICA IDENTITY DEFAULT`), leaving a departed row in the replica. Aggregate subscriptions keep the per-column prune, since only a column they read can move their value.
- A `timestamptz` crosses to a SQLite replica as the UTC text `YYYY-MM-DD HH:MM:SS.ffffff+00:00` from `emit::pgbinary_patchset` and from every CDC emit path, through `sqlite-diff-rs` 0.14. The snapshot path failed on every `timestamp`, `timestamptz`, `date`, `time`, `numeric`, `json` and `jsonb` column with a not-yet-implemented decoder, and the CDC paths stored the source's own text, such as Postgres's `+00` offset, which SQLite's date functions and diesel's SQLite chrono types refuse. `timestamp`, `date` and `time` likewise land in one text form per type whichever path carried them. A value no replica reader can hold, such as `infinity` or a year outside 1 to 9999, is now a decode error rather than stored text. A replica written by an earlier release keeps the old text, and an update or delete addresses its row by the primary key's new text, so a replica whose primary key includes a `timestamp`, `timestamptz` or `time` column needs a fresh snapshot.
