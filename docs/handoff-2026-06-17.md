## Bugs found and fixed during the proptest pass

The property test in `tests/proptest_register_batch_parity.rs` surfaced two real divergences between `register_batch` and a sequential `register()` loop. Both fixed in `95b435d`:

1. **Within-batch idempotent duplicates** got fresh `SubscriptionId`s in `register_batch` while a `register()` loop collapsed them onto the existing id. Fix: Phase 1 within-batch dedup map plus Phase 4 deferred reconciliation.
2. **Within-batch eviction visibility**: `pick_eviction_victim` only saw committed subscriptions, so when a later spec in the batch hit the cap the within-batch pending allocations were invisible to `EvictOldest` (and other policies, which need activity metadata pending subs do not have). Fix: when an active eviction policy is configured, fall back to a sequential `register()` loop. Bulk-COW fast path still applies for no-cap and `Reject` cases (the common startup-bootstrap cases).

Docstring on `register_batch` documents the parity contract explicitly.

## Recommended next steps in priority order

1. **Reliability-contract test suite**. The `connetto-rs` materializer-boundary doc (`docs/architecture/10-subscription-materializer.md`) lists five guarantees `subql` owes the materializer: triggers are repeatable, `install` is idempotent, in-process work is deterministic, no partial state, no silent drops. They hold by construction today but nothing tests them as a contract. Codify them in `tests/reliability_contract.rs`. Each test small and targeted; the suite locks behaviour against drift. Highest value because connetto-rs's retry / coalesce / replay loop relies on these.

2. **`no_std` build verification**. The crate claims `no_std + alloc` support. After the throttle and cursor work landed in this session, the `wasm32-unknown-unknown` target has not been re-verified. Likely a small CI matrix add plus any fix-ups.

3. **Panic audit**. Every `unwrap` / `expect` / `panic!` in `src/` either gets a justifying comment or converts to `Result`. Tedious but the resulting code is operationally safer. Probably 3-5 panics that genuinely should be errors hiding in the codebase.

4. **Reconnect / catchup integration test against connetto-rs**. The resume cursor is committed but never exercised end-to-end. Once connetto-rs starts using `advance_cursor` / `cursor_for`, a smoke test that round-trips through both sides would catch any contract drift early.

Lower-value items I considered and would deprioritise:

- Additional proptests over dispatch and aggregate code. Existing coverage is good and the marginal bug-discovery rate is low (the parity proptest was the productive one because it targeted code that landed in this session).
- Soundness audit batch D. Worth doing eventually but hand-written audits are most productive after substantial new code lands. Right now the recent surface area is small.
