# Proposal: `MysqlConnection::last_insert_id()` for diesel

Status: draft, intended for upstreaming to `diesel-rs/diesel`. Written against
diesel 2.3.x. Prompted by a concrete downstream need in `subql` (see the last
section) but useful to every diesel MySQL user.

## Summary

Add a first-class accessor on diesel's `MysqlConnection` that returns the
auto-increment key generated by the most recent statement, reading it from the
MySQL client library with no extra round trip:

```rust
impl MysqlConnection {
    pub fn last_insert_id(&self) -> Option<NonZeroU64>;
}
```

This mirrors the existing `SqliteConnection::last_insert_rowid() -> Option<NonZeroI64>`
and closes the one gap among diesel's built-in backends for "get the id of the
row I just inserted."

## Motivation

Retrieving a database-minted `AUTO_INCREMENT` key after an insert is one of the
most common operations against MySQL. Diesel's other backends already have a
clean answer:

- **Postgres / SQLite / MariaDB** support `RETURNING`, so diesel's typed
  `insert_into(..).returning(..).get_result(..)` hands the key back directly.
- **SQLite** additionally exposes `last_insert_rowid()` as connection sugar.
- **MySQL** (Oracle, through 8.4) has no `RETURNING`, and diesel exposes no
  `last_insert_id` accessor. So today the only options are a raw query or a
  hand-defined SQL function:

  ```rust
  // Untyped, boilerplate, and an extra server round trip:
  #[derive(QueryableByName)]
  struct LastId { #[diesel(sql_type = BigInt)] id: i64 }
  let id = sql_query("SELECT CAST(LAST_INSERT_ID() AS SIGNED) AS id")
      .get_result::<LastId>(conn)?.id;
  ```

The MySQL C client already computes and holds this value locally after every
statement (`mysql_insert_id()`), so a `SELECT LAST_INSERT_ID()` round trip is
pure overhead. A thin accessor is strictly better: no query, no result-set
decode, typed, and consistent with the SQLite precedent.

## Prior art in diesel

`SqliteConnection::last_insert_rowid` (`diesel/src/sqlite/connection/mod.rs`):

```rust
pub fn last_insert_rowid(&self) -> Option<NonZeroI64> {
    NonZeroI64::new(self.raw_connection.last_insert_rowid())
}
// raw.rs
pub(super) fn last_insert_rowid(&self) -> i64 {
    unsafe { ffi::sqlite3_last_insert_rowid(self.internal_connection.as_ptr()) }
}
```

Note the shape: `&self` (client-side state, not a query), `Option<NonZero_>` to
encode "no id was generated," and a documented caveats block. The MySQL version
should follow the same shape.

## Proposed API

```rust
impl MysqlConnection {
    /// The `AUTO_INCREMENT` value generated by the most recent statement on
    /// this connection, or `None` if the last statement generated none.
    ///
    /// Reads the value the MySQL client library holds locally
    /// (`mysql_insert_id()`); it performs no query. Read it immediately after
    /// the insert, before running another statement on the same connection
    /// (see Caveats).
    pub fn last_insert_id(&self) -> Option<NonZeroU64>;
}
```

Design choices:

- **`NonZeroU64`.** `mysql_insert_id()` returns `my_ulonglong` (u64), and MySQL
  `AUTO_INCREMENT` columns can be `BIGINT UNSIGNED`, so u64 is the faithful
  width. `0` is the library's "no value generated" sentinel, so wrapping it as
  `None` both encodes that in the type and matches SQLite's `Option`. A caller
  that wants `i64` does `u64::from(nz).try_into()`.
- **`&self`, not `&mut self`.** It reads client state, exactly like SQLite.

## Implementation sketch

The FFI is already available: `mysqlclient-sys` binds
`pub fn mysql_insert_id(mysql: *mut MYSQL) -> my_ulonglong` (verified in
`mysqlclient-sys` 0.5.1 across its bundled bindings). Diesel's
`mysql/connection/raw.rs` already wraps `NonNull<ffi::MYSQL>` and calls
`ffi::mysql_*` throughout, so:

```rust
// mysql/connection/raw.rs
pub(super) fn last_insert_id(&self) -> u64 {
    unsafe { ffi::mysql_insert_id(self.0.as_ptr()) }
}

// mysql/connection/mod.rs
pub fn last_insert_id(&self) -> Option<NonZeroU64> {
    NonZeroU64::new(self.raw_connection.last_insert_id())
}
```

No new dependency, no trait change, gated by the existing `mysql`/`mysql_backend`
feature. `mysql_affected_rows` is bound the same way and could get a sibling
`affected_rows()` accessor if desired, though that is out of scope here.

## Semantics and properties

`mysql_insert_id()` (the C API, per the MySQL reference manual) returns:

- The first `AUTO_INCREMENT` value generated by the most recent `INSERT` or
  `UPDATE`. For a **multi-row insert it is the FIRST row's id**, not the last;
  the remaining rows are contiguous under the default increment.
- The value set by `LAST_INSERT_ID(expr)` if a statement used it.
- `0` when the previous statement generated no `AUTO_INCREMENT` value (a table
  with no such column, an insert that supplied the key explicitly, or a
  non-generating statement). This maps to `None`.
- **Per-connection.** It is never affected by inserts on other connections, so
  it is safe under connection pools (each pooled connection has its own value).

Two divergences worth calling out in the docs, because they surprise people:

1. **C API vs the SQL `LAST_INSERT_ID()` function.** They agree for the common
   "insert a row, read the id" case, but differ in edge cases (notably
   `INSERT ... ON DUPLICATE KEY UPDATE` and explicit `LAST_INSERT_ID(expr)`
   interactions). This method returns the C API value, which is what callers
   almost always want. The doc comment should state that plainly.
2. **It is per-statement client state, not transactional.** The value reflects
   what the last statement generated. A later `ROLLBACK` does not change what
   `last_insert_id()` reports even though the row is gone, and any subsequent
   statement on the connection overwrites the value. So: read it right after the
   successful insert.

## Caveats (doc-comment block, mirroring SQLite's)

- Returns `None` (`0`) when the last statement generated no `AUTO_INCREMENT`
  value.
- Multi-row insert returns the first generated id.
- Reflects the most recent statement only; read it before issuing another.
- Not reset by `ROLLBACK`; it is client-side state, not committed state.
- `INSERT ... ON DUPLICATE KEY UPDATE` and `LAST_INSERT_ID(expr)` have the
  documented C-API semantics, which can differ from the SQL function.

## Testing

Mirror SQLite's `last_insert_rowid` tests, run against a live MySQL (diesel's
existing MySQL test harness / `DATABASE_URL`), gated on the `mysql` feature:

- **Fresh connection** -> `None`.
- **Single insert** into an `AUTO_INCREMENT` table -> `Some(1)`, then a second
  insert -> `Some(2)`.
- **Multi-row insert** of N rows -> the first row's id (e.g. after `INSERT ...
  VALUES (..),(..),(..)` following ids 1..3, the value is the first: verify it
  is the first, not the last).
- **No `AUTO_INCREMENT` column** -> `None`.
- **Explicit key supplied** -> `None` (verify against the server; the C API
  returns 0 when no value is auto-generated).
- **Per-connection isolation:** insert on connection A, assert connection B's
  `last_insert_id()` is unaffected.
- **Overwrite:** after an insert (`Some(1)`), run a `SELECT`, assert the value is
  what the driver reports afterwards (documents the "read immediately" caveat).

A doctest in the method (like SQLite's) doubles as usage documentation.

## Alternatives considered

1. **Raw `SELECT LAST_INSERT_ID()`** (status quo). Untyped, an extra round trip,
   `QueryableByName` boilerplate, and it returns the SQL-function value (subtly
   different from the C API in edge cases).
2. **A user-defined SQL function** via `define_sql_function!` +
   `diesel::select(last_insert_id())`. Typed, but still a round trip and still
   the SQL-function semantics.
3. **The proposed accessor.** No round trip, typed, reflects the value the
   client already holds, and matches the SQLite ergonomics diesel already ships.

## Compatibility and rollout

- Purely additive: one new inherent method on `MysqlConnection`, gated on the
  existing MySQL feature. No trait changes, no breaking changes.
- Needs a CHANGELOG entry and the doc/caveats block above.
- Optional follow-up: a sibling `affected_rows()` over `mysql_affected_rows`,
  and/or documenting the `RETURNING`-vs-`last_insert_id` split across backends
  in the guide.

## Downstream impact (why this is concrete, not hypothetical)

`subql` (a CDC subscription engine) has a "follow the row you just inserted"
feature. On Postgres it uses `RETURNING` through a typed diesel insert. On MySQL,
lacking `RETURNING`, it must read the minted key separately and currently does so
with the raw `SELECT LAST_INSERT_ID()` shown above (`tests/follow_insert_mysql.rs`,
tracked in `MILESTONES.md`). With this accessor that becomes:

```rust
diesel::insert_into(users::table).values(users::name.eq("ann")).execute(conn)?;
let id = conn.last_insert_id().expect("auto-increment id");
engine.follow_row(consumer, "users", vec![Cell::Int(i64::try_from(id.get())?)])?;
```

More broadly, "insert then get the id" is the single most common MySQL write
pattern, and diesel is the only mainstream Rust ORM/query-builder that makes its
MySQL users drop to raw SQL for it.
